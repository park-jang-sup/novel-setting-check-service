# 미니 PRD — novel-setting-check 서비스 (MVP)

**1) 한 줄 정의**  
연재 작가가 새 회차를 올리기 직전에, 회차 원고와 저장해 둔 설정집을 대조해 설정오류·확인필요·추가제안을 보여준다. 작가가 만든 세계를 서비스가 대신 기억한다.

**2) 타깃 사용자**  
50화 이상 연재 중인데 설정집 없이 쓰는 웹소설 작가. "있으면 편한" 사람이 아니라 "없으면 독자가 먼저 지적하는" 사람.

**3) 문제**  
회차가 쌓일수록 인물 나이·이름 표기·시간선·능력 설정·신규 고유명사가 흔들리는데, 대조할 설정집이 없으면 연재 후에야 지적받는다. 연재 직전 스스로 잡아주는 장치가 없다.

**4) 트리거**  
새 회차 올리기 직전. 장기휴재 후 연재 재개할 때도 부른다. 웹 서비스는 URL로 언제든 오지만, 실제로는 회차를 쓰는 흐름 속에 들어온다.

**5) 핵심 기능**

P0(결선 데모 필수, 5개)
- P0-1: 회차 원고 입력 → 규칙 기반 후보 추출 + Solar 1회 호출로 분류 → 추가제안 목록 생성. 설정집이 없어도 동작한다.
- P0-2: 추가제안 목록에서 사용자가 승인한 항목만 설정집에 들어간다. 자동 반영은 없다.
- P0-3: 설정집 + 회차 원고로 설정충돌/확인필요 검출. (novel-setting-check 스크립트 호출)
- P0-4: 설정집 브라우저 저장 상태 표시 + 초기화 버튼.
- P0-5: 설정집 자동 생성 — Solar 1회 호출로 원고에서 인물·용어(고유명사, 물건, 기술 등) 추출 → 추가제안 목록 → 사용자 승인 → 설정집 생성. 스킬은 "설정집 없으면 만들어 달라고 요청"으로 끝나지만, 웹에는 요청할 상대가 없어서 서비스가 대신한다.

P1
- 저장 예시가 필요한 사용자를 위한 설정집 템플릿 예시 제공.
- 회차 여러 개 요약/축적 기능은 이번에는 제외.

**6) 스킬 매핑**
- 기능별로 사용할 예선 스킬: novel-setting-check 1개.
- 웹에서는 회차 검사 기능을 Vercel 파이썬 서버리스 함수(`api/check.py`)로 실행한다. 실제 스크립트는 `skills/novel-setting-check/scripts/check_setting.py`를 그대로 쓴다. 원본 스크립트는 한 글자도 고치지 않는다. 임시 파일로 실행하는 것은 원본이 받는 입력이 파일 경로이기 때문이다.
- 아래 5개는 그대로 유지한다.
  ① 검출 5종: age_conflict / ability_candidate / timeline_reverse / name_variant / proposed_additions
  ② 설정집 마크다운 형식: `# 등장인물` / `# 지명` / `# 시간선` 섹션, 인물 필드는 별칭·나이·소속·불가·비고
  ③ JSON 출력 형식: summary / violations / proposed_additions / not_checked / errors (violations type, severity, line, subject, detail, context, repeated)
  ④ 체계: 스크립트 실행 → JSON 출력 → 그 JSON만 근거로 답. 스크립트 실행 없이 답하지 않는다.
  ⑤ 설계원칙 4개:
    - 검사하지 못한 것을 문제없다고 말하지 않는다.
    - 설정집을 임의로 수정하지 않는다.
    - 스크립트가 찾지 않은 오류를 지어내지 않는다.
    - 원고를 직접 읽어 판단하지 않는다.

- 실제 원고에서 안 잡히던 이유(실측: A-0 실행, 원고 12,263자, 설정집 인물 7명·지명 3개·시간선 5개, 결과 violations 10건·전부 오탐, proposed_additions 311건, not_checked []):
  1) age_conflict가 안 잡혔다. 설정집에 유진혁 나이 19가 있지만, 원고에서 나이와 다르게 읽힐 수 있는 표현은 두 가지다. 라인 3에 "만 19살 성인이 되는 날"(값 19, 설정과 같음)과 라인 14에 "스무 살 인생에 혹시라도"(값 20, 설정과 다름)가 있다. 스크립트는 나이 표현을 find_ages로 찾고, 그 표현이 설정집 인물명/별칭과 같은 윈도우(앞 60자 + 뒤 20자) 안에 있을 때만 age_conflict로 잡는다. 라인 14의 "스무 살" 앞뒤 60+20자 윈도우에는 '유진혁'도 '진혁'도 없어서, 20 ≠ 19를 스크립트가 보고도 충돌로 만들지 않았다. 즉 나이 표현과 인물명이 함께 나온 문장만 대조하므로, 인물명 없이 나이만 나오는 서술은 대조를 못 하고, 사용자는 그 상태를 알 수 없다. 이것은 명백히 잘못된다.
  2) timeline_reverse가 안 잡혔다. 설정집 시간선 5개 중 원고 등장 횟수는 다음과 같다.
     - 수능: 2회, 라인 3
     - 탑 등장: 0회
     - 튜토리얼: 4회, 라인 3·5·7·9
     - 불심검문: 1회, 라인 5
     - 베나토르 합류: 0회
     이 스크립트는 본문에 있는 사건만 모아 순서 역행이 있는지 본다. "탑 등장"과 "베나토르 합류"는 0회라 대조 대상이 아니고, 남은 3개 중 2건 이상 matched 조건이라 한 건(탑 등장)을 못 읽었다는 사실이 드러나지 않는다. not_checked에도 들어가지 않는다.
  3) name_variant가 오탐이었다. 오류를 심지 않은 원고에서 일반 명사를 인명 오타로 판정했다. 이번 실행 예: 이어진/이미 → 이무진, 감정 → 김수정, 저녁/전혀 → 진혁, 관문 → 광화문, 심정 → 수정, 성분 → 서울, 물건 → 박무건. 서로 다른 인물도 같은 방식으로 오답 처리했다(예: 김태진 → 김진규). 즉 오타와 그냥 다른 이름을 구분하지 못한다.
  4) 규칙만으로 인명·용어·일반어를 가르지 못한다. proposed_additions 311건도 대부분 일반어·고빈도어라 실제 설정집 추가 후보는 적고, 단어 빈도/표기 유사도만으로는 의미 있는 후보 추출이 어렵다.
  5) 추가로 심은 실제 오류(스킬 이름이 쾌속에서 질주로 바뀜)는 검출되지 않았다. 이번 검출 5종에는 이 유형(회차 간 인물-능력/용어 표기 변동)이 없다. 잡았다면 ability_candidate 계열로 볼 여지는 있지만, 현재는 인물-능력/용어 표기를 회차 간에 비교하는 항목 자체가 없어서 못 잡는다. 이 유형은 추가나 수정이 필요하다.
  - not_checked가 []인 이유: 나이·불가·시간선 모두 설정집에 있어서, 스크립트가 not_checked를 넣는 조건을 만족한 항목이 없었다. 다만 "검사하지 못한 항목이 없다"와 "대조가 실제로 다 됐다"는 다르다. 위 1·2처럼 대조가 안 된 상태가 있어도 드러나지 않는 한계가 있다.

**7) 입력·출력**

입력
- 웹 화면 원고 텍스트(입력창). 새 회차를 넣을 때마다 한 번씩 넣는다.
- 설정집이 있으면 브라우저 localStorage에 저장된 마크다운을 그대로 스크립트 입력으로 쓴다.

출력
- 승인 전: 추가제안 목록(후보 이름/용어, 분류 결과, 등장 정보). 아직 설정집이 아니다.
- 회차 검사 시: 설정오류 / 확인필요 / 추가제안 + 각 항목의 원문 위치(line, context). script JSON 출력을 그대로 근거로 보여준다.

**8) 필요 설정**

표 ① 배포 연결
- Vercel 배포 커넥터. 값 취급 없음.

표 ② 서비스 키(Vercel 환경변수 — 이름·용도·발급처만, 값 금지)
- 키 이름: UPSTAGE_API_KEY
- 용도: 회차 원고를 넣었을 때 인물·용어(고유명사, 물건, 기술 등) 추출/분류용 Solar 1회 호출. 설정집 생성(P0-5) 단계에서만 사용한다.
- 발급처: Upstage
- 회차 검사 포함, 승인 버튼은 이 키를 호출하지 않는다. Solar은 원고를 새로 넣을 때 한 번만 동작한다.

표 ③ 사용자 프로필(웹 화면 입력 → localStorage 저장, 재방문 시 묻지 않음, 초기화 버튼 제공)
- 설정집 마크다운 텍스트 → 브라우저 localStorage 저장.
- 자동 반영 없음. 생성·제안은 하지만 승인 전에는 설정집에 들어가지 않는다. 사용자가 승인한 항목만 설정집에 추가한다. 스킬 규칙과 동일: 사용자가 요청할 때만 추가.
- 초기화 버튼 제공.

**9) 데이터 규칙**
- 회차 기준 시점·출처를 표시한다.
- 없는 값은 "확인 불가"로 두고 추정하지 않는다.
- 키·프록시 주소는 서버 측에만 둔다. 클라이언트 소스·응답 JSON에 키를 넣지 않는다.
- 검출은 스크립트 JSON 출력만 근거로 한다. 스크립트가 찾지 않은 오류를 추가로 지어내지 않는다.

**10) 성공 기준**
- 데모 시나리오로 검증 가능한 조건.
- 시크릿 창 테스트 포함: 계정·저장값 없는 브라우저로 처음 방문했을 때 안내가 스스로 나오고, 최소 기능(회차 원고 입력 → 추가제안 목록)이 도는지.
- 설정집 없이 첫 회차를 넣었을 때 추가제안 목록이 나오고, 승인 후 두 번째 회차에서 대조 검사가 되는지.

**11) 제외 범위**  
할 수 있는데 의도적으로 안 하는 것만 적는다.

- 개연성, 캐릭터 붕괴, 문체 일관성 판단(이 서비스는 사실 대조만 한다).
- 문법·맞춤법 교정, 원고 첨삭, 문장 다듬기.
- 줄거리 요약·감상 평가.
- 자동 반영: 생성·제안은 하지만 승인 전에는 설정집에 들어가지 않는다 — 의도된 제한.

※ "설정집 없이 원고만 주는 경우"는 제외하지 않는다. 이건 스킬의 제약이지 서비스 제약이 아니다. 서비스는 P0-1로 추가제안 목록을 만든다. 이 서비스의 핵심 기능이다.

## 필드명 (UI 라벨 vs 저장 형식)

화면에 보여줄 라벨과 저장 형식은 다르게 쓴다. 저장 형식은 check_setting.py가 인식하는 다섯 개 그대로 간다. 다른 이름으로 쓰면 그 줄은 건너뛰어서 검사가 안 돈다.

| 화면 라벨 | 저장 형식(불가/비고 그대로) | 입력칸 힌트 |
|-----------|---------------------------|-------------|
| 별칭 | 별칭 | |
| 나이 | 나이 | |
| 소속 | 소속 | |
| 제약 | 불가 | 예: 마법, 비행 |
| 메모 | 비고 | |

화면에서 "제약"이라고 보여주고, 저장할 때는 "불가"로 쓴다.
